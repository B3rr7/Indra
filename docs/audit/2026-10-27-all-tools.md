# All-tools audit — 2026-10-27 (moto g60 / Android 16)

Every plugin registered in `PluginManager` (37) was opened on the device and driven far
enough to tell "this does real work" from "this only advertises a feature". "Works" below
means **observed on this phone**, with the tool's own output on screen — not "the code looks
right". The wireless plugins were covered in
[`2026-10-27-wireless-features.md`](2026-10-27-wireless-features.md); they are listed here
too so the table is complete, with a pointer instead of a second set of evidence.

Device context: moto g60, Android 16, mobile data on `rmnet_data2` (`10.161.185.30/30`,
gateway `10.161.185.29`), `wlan0` present but unassociated, daemon running as root
(`indrad`, core 1.0.2). MITM/`arpspoof` was **not** run: it hard-resets this phone (3/3).

## Findings

### F1 — nuclei could never start: `HOME` is `/` (fixed)
`nuclei` creates `~/.config/nuclei` before it reads anything, and the daemon's `HOME` is `/`
(read-only), so every run died with

```
[ERR] failed to create config directory at /.config/nuclei got: mkdir /.config: read-only file system
[FTL] Could not create runner
```

`-nc` (which the app already passed) does **not** skip the directory. `SmartToolBox.nuclei`
now runs through `shell()` as

```
mkdir -p <filesDir>/home && HOME=<filesDir>/home ./tools/nuclei/nuclei -silent -nc -u <target> …
```

(the daemon is root, so it creates the directory itself). `shell()` grew `label`/`timeoutMs`
parameters so the run keeps its 15-minute scan budget. Verified: the config error is gone and
nuclei reaches its next real failure (F2).

### F2 — Go binaries cannot resolve DNS inside the daemon (open)
Android has **no** `/etc/resolv.conf` (resolution goes through `netd`/bionic). Go's pure
resolver has no cgo fallback in these builds, so it defaults to `127.0.0.1:53`/`[::1]:53`:

```
$ ./tools/gobuster/gobuster dir -u http://example.com …
… dial tcp: lookup example.com on [::1]:53: read udp …->[::1]:53: read: connection refused
```

Same for nuclei (`lookup api.github.com …`, `lookup api.pdtm.sh …`). Consequences:

- **Gobuster** works for IP targets (verified) and fails for hostnames.
- **nuclei** additionally has **no templates**: `installNuclei` downloads only the binary, and
  `-update-templates` needs DNS, so it fails with `no templates provided for scan`.

Options, in order of honesty:

1. **Install templates from the app** (`CoreManager.installNuclei` already downloads with
   OkHttp, which uses Android's resolver): fetch the `nuclei-templates` archive and extract it
   into `<filesDir>/home/nuclei-templates`. That makes nuclei real for IP targets.
2. **Resolve hostnames in the app** and hand the tools an IP (gobuster `-u http://<ip>/`,
   nuclei `-u http://<ip>/`) — changes Host-header semantics, so it needs a per-screen decision.
3. **Say so**: "the bundled Go tools need an IP; hostnames cannot be resolved by the daemon"
   in the two screens' helper text.

Not fixed here: 1 and 2 are feature work, not audit remediation, and neither can be verified
without shipping templates.

### F3 — masscan cannot pick an interface (open)
`masscan` auto-detects the default interface by reading the routing table; on Android it gives
`[-] FAIL: could not determine default interface`. Explicit `-e` gets further but the cellular
interface is `LINUX_SLL`, which masscan rejects (`arptype 519 not supported by libpcap`), and
`lo` opens but transmits nothing (`rate: 0.00-kpps`, `100.00% done, waiting …`). So on this
phone the tool cannot scan at all — the screen shows masscan's own error, which is honest.

Fix: pass `-e <active iface>` (a `NetworkHelper.getActiveInterfaceName()` over
`ConnectivityManager`/`LinkProperties`), which is what makes it work on Wi-Fi. It cannot be
verified on this device: `wlan0` is unassociated and the only in-range networks are off-limits.

### F4 — a stale client flag made every gate say "daemon not running" (fixed)
Observed twice in one sweep: `indrad` was alive (`ps -A | grep indrad` → root, pid 27380) while
Masscan and then Packet Forger answered `Native daemon is not running — install the core and
start it in Settings → Native Core.`, and **every** later gate kept saying it until the app was
force-stopped. `isDaemonConnected()` is `libraries && !hasStartFailed() && connected &&
authenticated` — all client-side, and a single refused start (`noteStartResult(false)`) latched
`startFailed` with no reset path, because the gate itself refused to attempt another start.

Fixed: `CoreManager.reconnect()` (attach-only — it never starts a daemon, and returns
immediately when the socket file is gone, so it can't fire an `su` prompt) and `requireTool`
calls it once before believing the daemon is down. Verified on the device: Port Scanner →
IPTables back to back now runs `iptables -L -n -v` and lists real chains, where it previously
reported "daemon not running".

The deeper fix (the native client's reader thread should clear `connected` when the peer dies)
still needs a native rebuild — this is the app-side mitigation.

### F5 — Responder is registered but unreachable (open)
`PluginAvailability.isFeasibleOnAndroid()` hardcodes `id != "responder"`, so the card is
`UNSUPPORTED` and not openable — while `ResponderViewModel` is a working LLMNR responder
(binds UDP 5355, parses the question, answers with the device's IP). Either delete the plugin
+ screen, or unblock it behind a real precondition: it needs Wi-Fi (`WifiManager.connectionInfo`
returns `0` on mobile data, so the answer would claim `0.0.0.0`) and location permission on
Android 12+.

### F6 — Network Topology has no data source (open, already tracked as `2.4`)
`TopologyViewModel.setGraph/addNode/addEdge` have no caller anywhere in the app, so the canvas
is always empty while the screen invites the user to "Add nodes via the Network Radar / Port
Scanner results".

### F7 — Arsenal ships no templates (open, minor)
The screen is a user-authored command library; on a fresh install the list is empty, so the
plugin looks like a blank page. It works (verified end-to-end), it just has nothing to offer
until the user writes a command. A handful of seeded, obviously-safe templates would make the
feature discoverable.

## What this audit changes

- `core/system/SmartToolBox.kt`: `nuclei()` runs with a writable `HOME` (F1); `shell()` takes
  `label`/`timeoutMs`; `requireTool()` re-attaches once before reporting a dead daemon (F4).
- `core/system/CoreManager.kt`: new `reconnect()` (attach-only, F4).
- Everything else in the table above already behaved honestly on the device; the open findings
  are recorded here rather than papered over.
